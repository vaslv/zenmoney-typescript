# Usage and integration

The candidate is local and private. After `./scripts/pack.sh`, install
`.local/release/zenmoney-typescript-0.1.0.tgz` using npm. After an authorized npm
publication the same root imports work by package name. Only the root export is
supported; do not import internal dist/source modules. See ../examples/recipes.ts
for compiled examples of every financial builder and recurring objects.

## Read, persist and write

`new ZenMoneyClient({token, fetch?, clock?, timeoutMs?, maxResponseBytes?})` performs
no network I/O. `fetch` is trusted caller code: it receives credentials. Production
origin and paths are fixed; injection is for testing or a trusted transport layer.
The clock returns seconds as a safe integer or bigint. Entity IDs may be injected
with builder `id`; otherwise a UUID is generated by native crypto.randomUUID.

`readDiff({serverTimestamp: 0})` requests initial state. Apply returned entities and
deletions to your store, then commit the returned cursor atomically with the data.
Use that cursor on the next call; the SDK never persists or advances it internally.
`diff({serverTimestamp,changes,deletions,forceFetch})` combines collections explicitly.
`forceFetch` excludes country; observed country and future fields remain readable.

`upsert(kind, objects, {serverTimestamp?,signal?})` accepts complete wire objects.
`delete([transactions.deletion(kind,id,{user})])` uses stamped deletions. Budget
identity is user/date/tag, not id: use `clearBudget` then `upsert('budget', [value])`.
`entityKey` returns the reference-compatible string/composite identity.
`transactions.update(entity, fields, {now?})` copies, preserves extensions and stamps
changed; identity and created/changed overrides through fields are rejected.

`suggest(object)` returns one object; `suggest([objects])` returns an equal-length
array. The SDK preserves all returned fields and does not apply suggestions to your
store. All API methods accept per-call `signal` and issue at most one HTTP send.
Close is idempotent, permanent and aborts only the client's active calls. A shared
injected fetch remains usable by other clients. Keep a client alive for repeated
requests; close it when its owner finishes.

## Financial recipes

```ts
import {transactions, entities, decimal} from 'zenmoney-typescript';
const common = {user: 1, date: '2026-01-15', account: 'a', instrument: 1};
const expense = transactions.expense({...common, amount: decimal('12.34'), viewed: false});
const income = transactions.income({...common, amount: decimal('100.01')});
const refund = transactions.income({...common, amount: decimal('2.34'), categories: ['original-expense-tag']});
const transfer = transactions.transfer({user: 1, date: common.date,
  fromAccount: 'a', toAccount: 'b', fromInstrument: 1, toInstrument: 2,
  amountOut: decimal('20.00'), amountIn: decimal('19.12')});
const loan = transactions.debt({...common, debtAccount: 'existing-system-debt-account',
  action: 'lend', amount: decimal('10.00'), payee: 'Synthetic counterparty'});
const category = entities.tag({user: 1, title: 'Example', fields: {showIncome: false}});
```

Debt actions `lend` and `repay` move ordinary account → debt account; `borrow` and
`collect` reverse it. Use the existing system debt account; account creation does
not accept type debt. Loan/deposit account creation requires capitalization,
percent, startDate, endDateOffset, endDateOffsetInterval in the `fields` bag.
Other catalog overrides and future properties also use `fields`. The low-level
`transaction` builder supports both movement legs directly.

For category splits create separate prepared transactions with explicit amounts;
multiple tags alone do not define split proportions. `tag:null` and `tag:[]` remain
distinct; neither promises to suppress ZenMoney automatic categorization. No SDK
policy predicts categories or forces new imports to viewed:false.

Reminder, ReminderMarker and Budget have exported models and complete-object
low-level write support, matching Python without inventing extra constructors.
A marker's state='deleted' and deletion of a marker entity are different operations.
The compiled recurring example shows their full wire structure.

## Exact values and forward compatibility

`decimal(string)` accepts finite JSON number syntax, including exponents; it is
immutable and supports toString/equals/compare. Integers can be safe number or
bigint. Unsafe integer numbers, nonfinite values, custom prototypes, getters,
cycles, sparse arrays and unsupported JSON values are rejected before sending.
Root option properties with undefined are omitted; protocol object/array undefined
is rejected. Numeric token/depth limits are explicit differences from Python.

Use `encodeJson`/`decodeJson` for storage or transport of these exact values; do not
round-trip through JSON.parse/stringify. Unknown fields including nested numeric
values and inert __proto__ keys are retained. `Diff.rawJson` preserves original
UTF-8 response text, whitespace and an initial BOM. Raw replies may contain private
financial data: decide whether and how to persist/log them in your application.

## Errors and unknown outcomes

All SDK errors extend ZenMoneyError with category and safe code. ValidationError
means local validation failed; HTTPError adds statusCode. ResponseError means a
reply was invalid/oversized; TransportError has network/timeout/aborted code;
ClientClosedError means the owner closed the client. Native redirect failures are
TransportError without fabricated status. Errors do not retain response bodies,
request headers or original causes. Do not log the token or caller configuration.

Any failure after dispatch may leave an unknown write result. Persist prepared
objects and IDs before sending. Read/reconcile them after an error; then let your
application explicitly decide whether to resend. A successful reply is not a local
transaction commit. Matching, deletion tombstones, delivery journals, migration
and deduplication remain application responsibilities.

## Optional OAuth on a trusted server

```ts
import {authorizationUrl, callbackCode, OAuthClient} from 'zenmoney-typescript';
// Generate and persist unpredictable state in the calling application's session.
const url = authorizationUrl({clientId, redirectUri, state});
// After the application's redirect handler receives its original callback URL:
const code = callbackCode(callbackUrl, {expectedState: state});
const oauth = new OAuthClient({clientId, clientSecret, redirectUri});
try {
  const token = await oauth.exchangeCode(code);
  // Persist token.accessToken / token.refreshToken privately if required.
  // Call oauth.refresh(token.refreshToken) explicitly when appropriate.
} finally { oauth.close(); }
```

OAuthToken exposes accessToken/tokenType/expiresIn/refreshToken; normal string,
JSON and Node inspect representations are redacted. Direct access/devtools can
still reveal secrets. There is no secret storage, refresh scheduler, PKCE claim or
interactive browser login in the SDK. Registered-application live OAuth remains
unverified; a Bearer token is sufficient for data API use.

Browser bundling requires no Node polyfills. A normal page depends on API CORS;
MV3 workers need https://api.zenmoney.ru/* host permission granted by the application.
The package never grants permissions or accesses bank sessions.
